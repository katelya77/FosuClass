# R50.2 Unified Native Widget System + Interaction Semantics Closure Design

Date: 2026-08-19
Branch: `feat/campusflow-adp-integration`
Baseline PR: #49
Baseline HEAD at design start: `ac15f0581c9930e3b2b568c9be150d8ef06f47ee`
Status: Design approved in chat; implementation plan pending user review of this spec.

## 0. Purpose

R50.2 is the next competition-stage architecture after R50.1/R50.1.2 control-plane convergence. It has two inseparable goals:

1. close the remaining **human-intent / tool-selection / optional-parameter** gaps exposed by real ADP global-debug tests;
2. introduce a **Multi-Agent-native, reusable result Widget system** for the R50 tool/runtime model without falling back to the old 01~05 Workflow-only Widget architecture.

R50.2 must not make incorrect behavior merely look better. The semantic interaction gate therefore runs before Widget cutover.

---

## 1. Frozen baseline and invariants

The following remain frozen unless a failing acceptance case proves a narrowly-scoped compatibility fix is required:

- Multi-Agent topology: Main + Schedule + Risk + Insight.
- Transfer topology: Main -> children; each child -> Main; no child -> child semantic handoff.
- New-turn ownership: Main-first.
- CampusTools operation count: **13 unique Agent Tool operations**.
- Agent bindings: **14 bindings**, with `campus_academic_context` as the only shared CampusTool.
- Main binds no CampusTools; it retains `KnowledgeRetrievalAnswer` and Agent transfers.
- Tool Direct Result stays OFF.
- Runtime data stays `competition-demo-v3`.
- CloudBase endpoint/token contract stays unchanged.
- No production dataset, real university identity, real timetable, token, NodeID, VarBizID or system-prompt secret may enter competition fixtures/docs.
- PR #49 stays OPEN / UNMERGED.
- No formal ADP release/publish in this stage.

R50.2 may add optional fields to existing tool contracts only when required for a generic semantic fix; it must not add a 14th operation by default.

## 2. Evidence from real ADP console tests

### 2.1 Direct tool validation

The user has now verified the new R50 tools in Tencent ADP custom-plugin validation, including:

- `campus_entity_search`
- `campus_academic_context`
- `campus_common_free_time_query`
- `campus_room_utilization_query`
- `campus_reschedule_feasibility`
- `campus_group_plan`

`campus_group_plan` direct validation returns `success=true`, `competition-demo-v3`, `evidence.verified=true`, and ranked candidates with both free-time windows and room candidates. This proves the façade/runtime itself exists and is callable.

### 2.2 Global-debug observations

The D1~D6 console probes revealed that some old acceptance prompts were too synthetic or too loosely specified. More importantly, three generic product-level issues were exposed:

#### Finding A — browse/list intent is over-clarified

A broad imperative such as “列出几位老师” triggered a clarification form before eventually using `campus_entity_search` in list mode.

This is not a tool failure. It is a **generic intent policy problem**: when the user clearly asks to browse/list a known entity category and no additional constraint is required to produce a useful result, the system should execute a safe bounded list instead of asking what kind of list they meant.

#### Finding B — reschedule optional-room normalization is not closed end-to-end

Direct `campus_reschedule_feasibility` validation succeeds when the target room is omitted, but global-debug produced `ENTITY_NOT_FOUND` with an empty room representation.

This indicates an **optional structured-field normalization gap** between model/ADP parameter serialization and the deterministic façade/runtime. `room`, when omitted or represented as `null`, `""`, whitespace, empty object or empty array, must be treated as absent rather than as a room lookup request.

The older D5 follow-up “那原来的 lesson-001 现在在哪上课” is also not a valid user-level acceptance test for `campus_entity_search`, because lesson IDs are not a supported entity-search category. A protocol-level lesson ID may remain in deterministic smoke tests, but user-level E2E must use natural campus language and/or a previously selected lesson action/context.

#### Finding C — availability discovery and planning recommendation are not separated strongly enough

A request equivalent to “两位老师第1周一起开会，给几个候选时段” routed to `campus_common_free_time_query` instead of `campus_group_plan`.

Both are semantically adjacent, but they serve different user goals:

- `common_free_time_query`: **availability discovery** — answer when all entities are free;
- `group_plan`: **planning recommendation** — produce ranked candidate plans, including suitable free-time windows and room/resource candidates.

This distinction must be expressed as a generic intent contract rather than special-casing one sentence.

### 2.3 Weekend-heavy plan ranking is not automatically a correctness bug

`campus_group_plan` currently ranks weekend all-day candidates highly because they maximize free periods and room availability. This is mathematically consistent with its current deterministic score, but can be less useful for typical academic meeting intent.

R50.2 must not silently assume “weekdays only.” Instead it will:

- preserve factual ranking from the tool;
- allow user language such as 工作日/周一到周五/不要周末 to constrain the query;
- make Widget presentation surface weekday/weekend clearly;
- reserve any new default ranking preference for a later deterministic product-policy decision with its own tests.

## 4. R50.2-A — Interaction Semantics Closure

### 4.1 Intent-family contract

Introduce/strengthen generic intent families in the shared prompt/policy layer. They describe **goal semantics**, not literal query strings.

Minimum families:

- `BROWSE_LIST`: user asks to list/show/sample entities without a necessary filter.
- `SEARCH_ENTITY`: user supplies a name/keyword/filter and expects matching entities.
- `AVAILABILITY_DISCOVERY`: user asks when multiple entities are simultaneously free.
- `GROUP_PLANNING`: user wants candidate arrangements/plans/meeting slots, especially when a ranked recommendation or room/resource is useful.
- `RESCHEDULE_SIMULATION`: user asks whether moving a known class occurrence to a target slot is feasible; this is What-if only.
- existing schedule/risk/ranking/overview families remain.

Prompt rules:

1. Do not clarify when a useful bounded answer can be produced safely from an explicit browse/list intent.
2. Clarify only when a missing field changes the meaning materially or is required by the selected deterministic tool.
3. Do not infer unsupported internal identifiers from user language.
4. Prefer `common_free_time_query` for pure availability questions.
5. Prefer `group_plan` for arrangement/planning recommendation intent.
6. Never say a simulated reschedule has been applied.

### 4.2 Optional structured-parameter normalization

At the lowest safe deterministic boundary before entity resolution, normalize optional values:

- `null`
- `undefined`
- empty string / whitespace
- empty array
- empty object where the field contract is scalar/optional

into “absent” for optional fields such as `target.room`.

Normalization must be narrow and schema-aware. It must not erase required fields or valid zero values.

Regression tests must reproduce the ADP-shaped empty representation that caused the global-debug failure.

### 4.3 Acceptance redesign

R50.1 D1~D6 are no longer treated as a sacred literal sentence set. R50.2 establishes two layers:

#### Protocol smoke

May use deterministic IDs/fixture details to validate façade behavior.

#### Product E2E

Uses natural user intents, paraphrase families and multi-turn continuity. It must not require a normal user to know a `lesson-xxx` fixture ID from a cold start.

Required product-level acceptance families include:

- broad list without unnecessary clarification;
- relative teaching-week resolution;
- common availability discovery;
- room/teacher ranking;
- group planning uses `group_plan`, not merely common-free lookup;
- reschedule simulation via a known/selected lesson context;
- no false mutation claim;
- no internal protocol fields in final user response.

### 4.4 R50.2-A exit gate

Before Widget work:

- all repo tests green;
- new generic intent tests green;
- ADP-shaped optional-room regression green;
- prompt compiler/check green;
- no operation-count or binding drift;
- no CloudBase deployment unless explicitly required and authorized;
- PR #49 stays open.

## 5. R50.2-B — Unified Native Widget System

### 5.1 Chosen approach

Use **Native Unified Widget System** as the new R50 Multi-Agent presentation architecture.

Do **not** build 13 independent Widgets for 13 tools.

Do **not** continue the old 01~05 Workflow Widget architecture as the primary runtime.

Reuse proven visual/action ideas and real Tencent Widget assets from the existing seven-widget work, but put a new R50/V3 adapter contract in front of the new Multi-Agent result presentation.

### 5.2 Why Agent Output Widget, not Tool Direct Output Widget

Tool Direct Result remains OFF because many requests require:

- tool-result interpretation;
- cross-domain handoff;
- multi-tool reasoning;
- user-friendly summarization;
- choosing the correct result variant.

The primary target is **Agent Output Widget** on result-oriented child Agents. Main remains text-first and clarification-capable.

Initial console policy:

- Main: Text output + clarification Widget where needed.
- Schedule: Unified Result Widget.
- Risk: Unified Result Widget.
- Insight: Unified Result Widget.

If Tencent console behavior proves that a single child output Widget cannot safely represent both conversational text and structured result variants, R50.2 will use a lightweight `message` variant rather than forcing Main into Widget output.

### 5.3 Canonical presentation contract

Introduce a deterministic adapter-level contract independent of raw tool JSON:

```text
CampusResultEnvelope
  version
  variant
  status
  title
  subtitle
  verified
  summary
  context
  sections[]
  actions[]
  displayMeta
```

Rules:

- Adapter may transform and select fields, but may not invent campus facts.
- Tool/internal fields such as `queryId`, `dataHash`, raw `rankContext`, raw `temporalContext`, Node IDs and tokens are not user-facing.
- `verified` may be displayed as a user-facing badge such as “已核验”, but the raw evidence object is hidden.
- Empty/error states are first-class variants, not ad-hoc prose.

### 5.4 Result variants

One unified Widget system supports at least these semantic variants:

1. `schedule` — day/week/range schedule.
2. `space` — classroom search and space availability.
3. `collaboration` — common free time and group-plan candidates.
4. `risk` — conflicts, rush warnings and self/compare risk.
5. `reschedule` — What-if feasibility only.
6. `ranking` — teacher load and room utilization.
7. `overview` — campus teaching overview.
8. `empty` — verified empty result.
9. `error` — recoverable tool/semantic failure.
10. optional `message` — lightweight structured result when a child must answer without a rich domain card.

Tool-to-variant mapping is many-to-one. This is intentional.

### 5.5 Interaction protocol

Use Tencent official Widget Actions only.

Primary continuation action: `sys.chat`.

Examples of semantic actions:

- 查看某一天 / 某一周
- 检查风险
- 看 Top2 / Top3
- 找共同空闲
- 生成会议候选
- 换校区 / 换教室条件
- 模拟另一个调课时段

Action payload must carry enough stable semantic context to continue the request without exposing internal implementation metadata in visible labels.

Do not put business computation inside Widget templates. Widget actions re-enter the conversation and let Main/child routing plus CampusTools perform new factual work.

### 5.6 Visual language

R50.2 should feel like one product rather than unrelated cards.

Shared design language:

- compact university productivity aesthetic;
- high information density without dashboard clutter;
- clear hierarchy: title -> key result -> evidence/constraints -> next actions;
- restrained color use; color conveys semantic state, not decoration;
- mobile-first card widths and typography;
- verified state visible but understated;
- weekday/date/period information scannable at a glance;
- ranking ties represented honestly;
- empty/error states include a useful recovery action.

Existing seven Widget assets are references, not immutable visual contracts. The new system may redesign them where needed.

### 5.7 Visual identity assets

R50.2 also prepares a coordinated identity package for:

- app avatar;
- Main avatar;
- Schedule avatar;
- Risk avatar;
- Insight avatar;
- CampusTools plugin avatar;
- optional conversation/background illustration if supported by the current console.

These assets must share one visual system while preserving role distinction.

Avatar work is presentation-only and must not change routing semantics.

## 7. Error handling

### Verified empty

Show an `empty` result only when the deterministic tool returns a successful, verified empty result.

### Tool/runtime failure

Show a recoverable `error` result or text fallback; do not fabricate data.

### Widget rendering failure

Fail open to concise natural-language output derived from the verified tool/Agent result. Widget failure must not break the factual answer.

### Action failure

If `sys.chat` action context is insufficient, Main may clarify the minimum missing user-semantic field. It must not expose protocol internals.

## 8. Testing strategy

### 8.1 Contract tests

- envelope schema validation;
- tool-result -> variant adapter snapshots;
- no internal-field leakage;
- action payload contract;
- tie/ranking rendering;
- empty/error rendering.

### 8.2 Semantic tests

- browse/list no-overclarification;
- availability vs planning tool selection;
- optional room normalization;
- reschedule no mutation claim;
- natural-language paraphrase families.

### 8.3 Widget tests

- local compiler/static validation;
- real Tencent Widget export/import contract;
- Agent Output binding validation;
- mobile layout smoke;
- `sys.chat` continuation back into Main-first routing.

### 8.4 Console pilot order

1. `ranking` pilot — simplest read-only structure.
2. `schedule` pilot — richer repeated rows and actions.
3. `collaboration` pilot — ranked candidate plans and rooms.
4. `risk` / `reschedule`.
5. `space`.
6. `overview`.
7. empty/error recovery.

Do not cut all children to Widget output at once. Each pilot must have a text rollback path.

## 9. R50.2 console acceptance

Console acceptance must be capability-family based rather than tied to six brittle literal questions.

Minimum real-ADP evidence:

- one generic browse/list request without needless clarification;
- one temporal relative-week request;
- one common-free request;
- one group-planning request that actually calls `campus_group_plan`;
- one ranking result including a tie case;
- one natural reschedule simulation with omitted room handled correctly;
- one Widget `sys.chat` continuation across domains;
- one verified empty state;
- one recoverable error state;
- no internal-field leakage;
- no mutation claim;
- no child -> child semantic transfer.

---

## 10. Rollback

R50.2 is introduced additively.

- Prompt semantics can roll back to R50.1 final prompts.
- Optional normalization fix must be isolated and reversible.
- Unified Widget assets do not overwrite old seven Widget exports until each pilot passes.
- Child Agent output can be switched back to Text independently.
- Old Workflow Widget artifacts remain historical rollback references, not the active architecture.

---

## 11. Non-goals

Not in R50.2:

- adding a fifth Agent;
- adding a 14th CampusTool operation by default;
- production timetable ingestion;
- real university binding;
- personal memory/alias subsystem;
- formal production or competition release;
- large-scale multimodal import;
- redesigning deterministic ranking policy without a separate explicit product decision.

---

## 12. Completion definition

R50.2 is complete only when:

1. interaction semantics closure is green;
2. unified result envelope and adapters are deterministic and tested;
3. at least the required result variants are implemented;
4. Schedule/Risk/Insight can use the unified Agent Output Widget architecture with text rollback;
5. `sys.chat` actions continue through Main-first routing;
6. real ADP console evidence is recorded;
7. repo/CI remain green;
8. PR #49 remains OPEN / UNMERGED;
9. no formal app publish occurs.

Only after this may the project move to the next stage such as multimodal schedule ingestion, personal context/alias memory, or final competition experience convergence.
