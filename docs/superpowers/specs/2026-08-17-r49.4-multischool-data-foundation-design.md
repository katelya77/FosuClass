# R49.4 Multi-School Anonymous Data Foundation — Design

## 1. Goal

Build the next ADP foundation for 「校园智序 · 小序」without binding the competition product to any single real university. R49.4 must simultaneously:

1. Fix ambiguous time-window semantics exposed by the current CASE D family.
2. Add deterministic week/range teacher-load and schedule-range capabilities instead of relying on prompt inference.
3. Define a privacy-first, multi-school schedule-ingestion architecture that can later accept legacy `.xls`, `.xlsx`, CSV/JSON, screenshots, and portal exports.
4. Preserve the anonymous competition build: no real university name, real student identifier, real teacher/class/course/room name, campus VPN address, or personal source file may enter competition fixtures, prompts, generated submission assets, screenshots, or Golden data.
5. Keep PR #49 open/unmerged and preserve the current R49.3 baseline as rollback.

This design is intentionally split into a first implementation slice and later slices. The first implementation slice is **R49.4 Semantic Window + Data Foundation**; image OCR/vision, live portal ingestion, long-term memory, official-web knowledge search, and UI polish are later independent slices.

---

## 2. Context and verified constraints

### 2.1 Existing architecture

R49-MA already establishes four agents: Main, Schedule, Risk, Insight. Dynamic campus facts are intended to come from deterministic CampusTools; the platform handles turn-to-turn routing while Main owns stale-context escape and cross-domain handoff.

Current `campus_overview` is a **fixed four-week aggregate**. It can produce overall teacher load TopN, but it does not expose a first-class `weekStart/weekEnd` query contract. Current `campus_schedule_query` is entity-scoped and single-week oriented.

Therefore the request:

> “看未来第一周课表负载最高的教师课表”

cannot be made fully deterministic by prompt rules alone. It requires a week-scoped load query followed by a schedule query for the resolved teacher.

### 2.2 Private reference source

A private user-provided timetable export is a legacy Microsoft Excel BIFF/OLE2 `.xls` file. The reference screenshots show a common legacy teaching-system timetable grid whose course blocks encode at least:

- course name
- teacher
- week expression
- room/building
- class period / time slot

The real file and screenshots are **reference-only**. They must never be committed, copied into test fixtures, included in reports, or used as competition screenshots.

### 2.3 Multi-school preparation

The competition build must not name or target a specific real institution. Real-world portal research is used only to inform adapter capability design. In committed competition-facing artifacts, adapters are identified by neutral provider families or capabilities, not institution names.

Initial compatibility targets are represented internally as:

- `portal-family-qz-legacy` — legacy Qiangzhi-style timetable/export family, including BIFF `.xls` exports.
- `portal-family-cas-a` — CAS/SSO + possible WebVPN protected portal; exact timetable vendor not assumed until a safe sample/export is available.
- `portal-family-cas-b` — CAS/SSO + student academic system + off-campus VPN path; exact timetable parser remains capability-driven.

No school name is embedded in these IDs.

## 3. Architecture decision

Use **Multi-Agent orchestration + deterministic Campus Data Hub + fixed ingestion workflows + source-aware Widgets**.

Do not solve new capabilities by continuing to append prompt exceptions.

### 3.1 Three truth planes

#### A. Anonymous Competition Data

Namespace: `competition-demo`

Purpose:
- judges/demo
- deterministic Golden cases
- anonymous teacher/class/course/room/campus entities

Rules:
- immutable by personal imports
- no real institution metadata
- remains independently buildable into submission package

#### B. Personal / Imported Schedule Data

Namespace: `personal-import`

Purpose:
- user-specific imported timetable
- user corrections
- user aliases
- later screenshot/portal imports

Rules:
- user-scoped
- never copied into competition fixtures or submission package
- versioned
- provenance retained
- raw upload retention minimized

#### C. External Knowledge / Portal Adapter Layer

Namespace: `external-source`

Purpose:
- parser/adaptor capability definitions
- official-web source connectors
- future school-specific integration profiles

Rules:
- competition-facing code uses neutral provider IDs
- real institution endpoints/credentials stay outside submission artifacts
- no credential scraping or VPN bypass behavior

## 4. R49.4 semantic-window model

R49.3 fixed the bug where `overviewWindow.count=4` polluted downstream `week=4`, but defaulting every drilldown to `week=1` is not semantically sufficient.

R49.4 replaces that shortcut with three explicit concepts:

```ts
interface WindowContext {
  rankingWindow: { weekStart: number; weekEnd: number } | null;
  detailWindow: { weekStart: number; weekEnd: number } | null;
  academicWeek: number | null;
}
```

### 4.1 Meaning

- `rankingWindow`: the time range used to compute TopN or load ranking.
- `detailWindow`: the time range requested for the detail view after an entity/rank is selected.
- `academicWeek`: a single teaching week only when the user explicitly specifies one or the downstream tool requires one and the intended week is unambiguous.

### 4.2 Required behavior

#### D1 — multi-week ranking

User: `未来四周教师负载最高的是谁？`

Expected:

```json
{
  "rankingWindow": { "weekStart": 1, "weekEnd": 4 },
  "selectedRank": null
}
```

#### D2 — range-preserving drilldown

Follow-up: `看Top1课表`

Expected:
- resolve `Top1 = teacherLoadTop[0]`
- **no clarification caused by a metric tie**
- inherit the ranking range as the detail range

```json
{
  "detailWindow": { "weekStart": 1, "weekEnd": 4 }
}
```

The system must not silently convert this to `week=1` and must not convert `count=4` to `week=4`.

#### D3 — narrow the detail window

Follow-up: `只看第一周`

Expected:

```json
{
  "detailWindow": { "weekStart": 1, "weekEnd": 1 },
  "academicWeek": 1
}
```

#### D4 — single-week rank + schedule in one request

User: `看未来第一周课表负载最高的教师课表`

Expected deterministic chain:

```text
teacher load query W1..W1
  -> stable Top1 entity
  -> schedule range query W1..W1 for that entity
  -> final answer/widget
```

No KnowledgeRetrievalAnswer fallback, no history arithmetic, no model counting schedules, and no Main↔Insight routing loop is acceptable.

### 4.3 Multi-week risk ambiguity

A follow-up such as `检查Top1风险` after a four-week ranking must **not** silently map to week 1. Until a range-aware risk tool is introduced, Main must either:

- use an explicitly stated week from the user, or
- issue one concise clarification asking which week/range to inspect.

R49.4 tests must avoid ambiguous risk wording when validating deterministic window behavior.

## 5. Additive deterministic tools

Existing tools remain backward compatible. R49.4 adds facades; it does not rewrite the frozen 01–04 fact semantics.

### 5.1 `campus_teacher_load_query`

Purpose: deterministic teacher-load ranking for an arbitrary teaching-week range.

Input:

```ts
interface TeacherLoadQueryInput {
  weekStart: number;
  weekEnd: number;
  topN?: number;       // default 3, bounded
  campus?: string;     // optional normalized campus filter
}
```

Output:

```ts
interface TeacherLoadQueryResponse {
  success: boolean;
  dataVersion: string;
  window: { weekStart: number; weekEnd: number };
  items: Array<{
    rank: number;
    teacher: { id: string; name: string };
    lessonOccurrences: number;
    periodUnits: number;
  }>;
  rankContext: {
    source: "campus_teacher_load_query";
    list: "teacherLoadTop";
    selectedRank: number | null;
  };
  evidence: { verified: boolean; source: string; computedAt: string };
  error: null | object;
}
```

Ranking is stable and deterministic:

1. `lessonOccurrences DESC`
2. `periodUnits DESC`
3. normalized teacher name / stable ID tie-break

Metric ties are reported as business ties but do not make positional Top1 ambiguous.

### 5.2 `campus_schedule_range_query`

Purpose: deterministic schedule detail across a teaching-week range.

Input:

```ts
interface ScheduleRangeQueryInput {
  entityType: "teacher" | "class" | "room" | "course";
  entityName: string;
  weekStart: number;
  weekEnd: number;
  weekday?: number;
  periodStart?: number;
  periodEnd?: number;
}
```

Output uses the same schedule item shape and evidence rules as `campus_schedule_query`, but every item includes its academic week and the response includes the explicit range.

### 5.3 Compatibility rule

- `campus_schedule_query` remains the preferred facade for a single explicit week.
- `campus_schedule_range_query` is used only when `weekStart != weekEnd` or when a rank drilldown intentionally preserves a multi-week range.
- existing R49.2.1 zero-mask semantics remain unchanged.

## 6. Agent-state contract changes

### Main

Main owns:

```ts
interface HandoffState {
  activeEntity: EntityRef | null;
  rankContext: RankContext | null;
  windowContext: WindowContext;
  staleContextEscaped: boolean;
}
```

Rules:
- current explicit user window overrides inherited windows
- rank entity can be inherited independently from the window
- domain-local state must not overwrite `windowContext`
- new-domain request drops unrelated pending state

### Insight

Insight:
- calls the fresh deterministic load tool whenever ranking window or ranking metric changes
- returns `rankContext + rankingWindow`
- never provides detailed personal schedule from aggregate data

### Schedule

Schedule:
- consumes `activeEntity + detailWindow`
- fresh tool call on every new turn that changes entity/window/day/period filter
- chooses single-week or range facade deterministically

### Risk

Risk:
- does not reinterpret multi-week `rankingWindow` as a single week
- self/compare semantics remain R49.3

## 7. Canonical Schedule Data Hub schema

The importer must normalize every source into one institution-neutral record shape.

```ts
interface CanonicalScheduleEvent {
  id: string;
  namespace: "competition-demo" | "personal-import" | "external-source";
  semesterId: string;
  course: {
    id?: string;
    name: string;
  };
  teachers: Array<{ id?: string; name: string }>;
  classes: Array<{ id?: string; name: string }>;
  location: {
    campus?: string;
    building?: string;
    room?: string;
  };
  time: {
    weekday: number;
    periodStart: number;
    periodEnd: number;
    startTime?: string;
    endTime?: string;
    weeks: number[];
    oddEven?: "all" | "odd" | "even";
  };
  source: {
    providerFamily: string;
    sourceType: "xls" | "xlsx" | "csv" | "json" | "image" | "portal-export";
    importedAt: string;
    sourceRecordId?: string;
    confidence: number;
  };
  raw?: Record<string, unknown>;
}
```

### 7.1 Required normalization behavior

- preserve the original source record in private provenance where practical
- normalize week expressions such as `1-14周`, `1,3,5周`, odd/even weeks
- split mixed campus/building/room strings without inventing missing fields
- support multiple teachers/classes
- preserve overlapping lessons rather than deduplicating them incorrectly
- validation failures are explicit and never silently repaired by the LLM

## 8. Schedule ingestion pipeline

```text
Upload / Export / Image
        ↓
Source Detector
        ↓
Provider Adapter
        ↓
RawScheduleRecord[]
        ↓
Canonical Normalizer
        ↓
Deterministic Validator
        ↓
Uncertainty Resolver
        ↓
Preview Widget
        ↓
User Confirm / Edit
        ↓
Versioned Personal Schedule Store
        ↓
Campus Data Hub query facade
```

### 8.1 First implementation slice

R49.4 implements:

1. canonical schema
2. provider adapter interface
3. legacy BIFF `.xls` adapter boundary
4. synthetic fixtures that mimic a legacy weekly timetable structure but contain no real names/data
5. canonical validation and week-expression parser
6. source/provenance metadata
7. privacy scanner to ensure source files and real identifiers cannot enter competition artifacts

R49.4 does **not** yet ship:

- credential login automation
- VPN bypass
- live campus portal scraping
- screenshot vision extraction
- official-web crawling
- user-facing import Widget

Those are later isolated slices.

### 8.2 Provider adapter interface

```ts
interface ScheduleSourceAdapter {
  id: string;
  supports(input: SourceDescriptor): Promise<number>;
  parse(input: SourcePayload): Promise<RawScheduleRecord[]>;
  normalize(record: RawScheduleRecord): CanonicalScheduleEvent[];
}
```

Adapters must be provider-family/capability based. A university name is never used as a parser key in the anonymous competition build.

## 9. Privacy and anonymity contract

### 9.1 Forbidden in competition artifacts

The submission build and all anonymous fixtures/prompts/reports must reject:

- real university names
- real student IDs/names
- real teacher names
- real class/course names from private imports
- real room/building/campus names from private imports
- private portal/VPN hostnames
- credentials, cookies, tokens, SSO tickets
- uploaded timetable filenames when they contain personal identifiers

### 9.2 Real-world compatibility notes

Actual institution names, portal URLs, and vendor observations are development research only. They must stay outside generated submission package and anonymous runtime fixtures.

### 9.3 Uploaded file handling

Default design:
- uploaded source is parsed in a private/user-scoped ingestion context
- raw file is not committed to Git
- normalized schedule is stored separately from competition-demo
- import preview shows source type and confidence, not the original local filename by default
- user can delete an imported schedule version

## 10. Multi-school compatibility strategy

Do not promise direct live-login support before samples exist.

### `portal-family-qz-legacy`

Preparation target:
- legacy BIFF `.xls`
- modern `.xlsx` export
- timetable grid parsing
- week/period/location normalization

This family can be implemented first because a private export sample exists, but the sample itself is never committed.

### `portal-family-cas-a`

Preparation target:
- authenticated campus portal behind CAS/SSO and possibly WebVPN
- first support safe **file/export ingestion**
- direct portal adapter waits for a sanitized HTML/export sample and verified access contract

### `portal-family-cas-b`

Preparation target:
- authenticated student academic system with off-campus VPN path
- first support safe export/import
- direct connector remains optional and must never attempt credential capture or bypass network controls

### Capability matrix

Every adapter records capabilities rather than school identity:

```ts
interface ProviderCapabilities {

  acceptsXlsx: boolean;
  acceptsCsv: boolean;

  supportsPersonalSchedule: boolean;
  supportsTeacherSchedule: boolean;
  supportsRoomSchedule: boolean;
  supportsCourseSchedule: boolean;
  supportsClassSchedule: boolean;
}
```

## 11. Future slices after R49.4

### R49.5 — Multimodal Schedule Studio

- image/file upload workflow
- vision model extracts structured timetable candidates
- deterministic validator checks week/weekday/period consistency
- missing/low-confidence fields become clarification cards
- user edits before commit
- no direct model-to-database write without confirmation

### R49.6 — Personal Memory & Alias

Memory stores preferences and aliases, not authoritative schedule facts.

Examples:
- `动医6 -> 某完整班级名称` is an alias memory
- `默认查看我的个人课表` is a user preference
- a lesson occurrence is stored in schedule data, not LLM memory

### R49.7 — Official Knowledge Intelligence

- source allowlist profiles
- official-domain discovery/search
- source title, publish date, retrieval time, citation URL
- stable documents may enter knowledge base
- time-sensitive notices use fresh web retrieval
- official-source facts remain separate from schedule facts

### R49.8 — Source-aware UI / Widgets

Widgets show neutral source badges such as:

- `匿名演示数据 · 已核验`
- `个人导入 · 已确认`
- `文件识别 · 1项待确认`
- `官方来源 · 已核验`

No real institution name is required for the competition demo.

## 12. Revised deterministic CASE D family

The old CASE D is replaced by unambiguous variants.

### CASE D1 — Multi-week ranking

1. `未来四周教师负载最高的是谁？`
2. expected fresh `campus_teacher_load_query(weekStart=1, weekEnd=4)`
3. metric ties reported, position Top1 remains deterministic

### CASE D2 — Preserve range on Top1 schedule

1. continue from D1
2. `看Top1课表`
3. expected `campus_schedule_range_query(entity=Top1, weekStart=1, weekEnd=4)`
4. no `week=1` fallback and no `week=4` contamination

### CASE D3 — Narrow detail range

1. continue from D2
2. `只看第一周`
3. expected fresh single-week schedule query for Top1, `week=1`

### CASE D4 — Single-turn week-specific composite

1. new conversation
2. `看未来第一周课表负载最高的教师课表`
3. expected two deterministic facts steps:
   - `campus_teacher_load_query(1,1)`
   - schedule query for returned position Top1 at week 1
4. KnowledgeRetrievalAnswer must not appear in the dynamic-fact chain
5. no Main↔Insight routing loop

### CASE D5 — Business tie vs position rank

When two teachers have equal metrics:
- response states they are tied on metrics
- stable `rank=1` and `rank=2` positions still exist
- `Top1` alone never triggers a teacher-choice clarification

## 13. Testing strategy

### Unit tests

- week-range validation (`1..20`, start <= end)
- deterministic teacher-load aggregation
- tie sorting
- week expression parser
- canonical schema validation
- provider detection confidence
- private source filename/identifier scrub

### Contract tests

- old five Agent tools remain backward compatible
- new load/range tools have matching CloudFunction + MCP schemas
- ADP OpenAPI descriptions forbid model-generated dynamic facts
- no source-school names appear in competition import assets

### Multi-turn tests

- D1–D5 above
- fresh tool call on changed window
- explicit week overrides inherited range
- new task drops old rank/window state

### Privacy tests

A build-time scanner fails if competition package contains configured forbidden private-source markers. The scanner configuration itself must use hashed or synthetic markers in committed code; real private names/IDs are supplied only through local environment during private validation.

## 14. Deployment and rollback

- R49.3 HEAD remains the rollback point.
- R49.4 first develops/tests locally and in repository.
- CloudBase deployment occurs only after deterministic local tests and PR CI are green.
- ADP prompt/tool imports occur only after tool schemas are stable.
- PR #49 remains OPEN / UNMERGED.
- no formal application publish during this slice.

A backup branch/ref may be created from the R49.3 checkpoint, but it is not merged into main and is not a competition release.

## 15. Acceptance gate for R49.4

R49.4 is PASS only when all are true:

1. CASE D1–D5 pass deterministically.
2. `未来第一周课表负载最高的教师课表` uses a week-scoped load tool and a schedule tool, not knowledge retrieval or model arithmetic.
3. multi-week Top1 drilldown preserves the ranking window unless the user narrows it.
4. old R49.2.1 schedule/risk/classroom/day-plan tests stay green.
5. legacy `.xls` source adapter interface and synthetic fixture tests pass without committing any real timetable data.
6. competition package scanner finds zero real-school/private-source markers.
7. no real portal credentials/URLs are introduced into anonymous competition assets.
8. PR #49 remains open/unmerged and no formal application release occurs.
