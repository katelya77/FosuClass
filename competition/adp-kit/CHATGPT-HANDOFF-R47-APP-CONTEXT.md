## 2. 产品定位

应用名称：**校园智序·小序**

定位：面向高校课程、教学空间与校园教学运行任务的智能助手 / 校园教学时空决策智能体。

核心原则：

1. 用户可以自然语言查询，但**动态校园事实必须来自确定性工作流 / CampusTools 工具核验**。
2. 工具失败、参数不足或数据不在演示范围时，不允许模型自行补造课程、教室、教师、冲突、教学态势等事实。
3. 静态功能说明、怎么问、功能示例、产品边界等可以直接回答，不必调用动态工具。
4. 当前为比赛匿名演示数据，不要猜测或渲染真实学校、真实老师、真实班级身份。
5. 查询/规划为只读能力；不做真实选课、改课、预约教室、写入教务系统等动作。
6. Widget 是核心演示体验之一，但 Widget 的视觉层不能反向篡改工具事实。

## 5. Widget 当前体系与关键历史坑

### 5.1 早期导入坑

曾出现：

- Widget 导入时报 `400-名称只能包含中文、英文、数字、下划线、中划线、空格`
- 工作流导入时报“文件数据存在错误”
- 工作流节点导入后报“未选择 Widget，请删除节点后重新添加”

原因之一：工作流 ZIP 中的 Widget 绑定信息不能靠猜 ID/名称硬造，Tencent ADP 导入后会重新生成真实 Widget identity。

后来采用正确方法：**先导入 Widget → 从 Tencent ADP 再导出真实 Widget 包 → 用真实导出 schema/identity 修工作流 → 再导入工作流。**

因此新对话如果需要继续生成可导入 ZIP：

- 不要手写/猜测 Widget ID
- 必须以用户“导入后再导出的最新 Widget 文件”为 binding truth
- 若 ADP 报 error 标注文件，先读 error 文件再改，不要盲改

### 5.2 曾经/当前 Widget 名称族

历史可见 7 个主 Widget：

- `小序-校园教学态势-R42`
- `小序-任务恢复-R42`
- `小序-空教室票据-R42`
- `小序-课表票据-R42`
- `小序-今日校园计划-R42`
- `小序-候选确认-R42`
- `小序-冲突赶场票据-R42`

后续工作流内部又出现 RuntimeSafe / Stable 版本，例如：

- `小序-空教室票据-RuntimeSafe-V3`
- `小序-冲突赶场票据-RuntimeSafe-V3`
- `小序-今日校园计划-RuntimeSafe-V3`
- `小序-任务恢复-RuntimeSafe-V3`
- `小序-课表票据-WidgetStable-DAY/WEEK/DATE`（历史阶段）

R46 新增了专门的整周课表 Widget，UI 中可见名称前缀：

- `小序-整周课表-R46-WEEK` / `小序-整周课表-R46-...`

**具体最新名称、内部 ID、input schema 一律以用户最新 ADP 导出包为准，不要只根据本文字符串复刻。**

### 5.3 Widget 交互当前结论

- 用户点击 Widget 自带按钮，应用层能正常响应并执行对应工作流/动作。
- 这说明 action payload / button path / 工作流能力本身大体正常。
- 当前问题主要是“用户不点按钮，而是自己输入等价自然语言短追问”时，上下文没有被顶层正确恢复。

这是 R47 诊断的重要分界：**不要为了修文字上下文，重写已经正常的按钮 action 链。**

## 8. 下一阶段建议名称：R47 Application Context Bridge

新对话接管后，第一阶段先做诊断和设计，不要直接大改 5 个工作流。

### 8.1 R47 目标

建立应用级连续对话的“任务状态桥”，至少能记住并复用：

- `last_task_type`：01/02/03/04/05
- `entity_type`
- `entity_name` / user-facing alias
- `week`
- `weekday`
- `date`
- `time_scope`
- `period_start / period_end`
- `campus`
- `min_capacity`
- 对比任务双方实体（03）
- 日计划 date / user context（04）
- Overview start/end/window（05）

同时识别短追问中的**增量修改意图**：

- 时间切换：`只看周三`、`周五呢`、`那整周呢`、`下一周呢`、`上一周呢`、`下一天呢`
- 校区切换：`换到B校区`、`C校区呢`
- 节次切换：`改成第3-4节`
- 容量筛选：`大于60人的呢`、`至少100人`
- 风险派生：`那有赶场风险吗`、`看看整周风险`
- 由结果派生到其他任务：课表 → 找空教室 / 风险；Overview → Top1 周课表/风险等

### 8.2 必须满足的行为

1. 如果本轮是可确定的 follow-up，不得重新追问已经在上轮确定的字段。
2. 只覆盖用户本轮明确修改的 slot，其他 slot 保留上一轮。
3. 若本轮明确切换任务类型，允许跨工作流，但要携带可复用实体/日期。
4. 只有在上下文确实不足或存在真实歧义时才追问。
5. 所有动态事实仍然必须落到对应工作流/工具，不允许顶层模型直接“凭上下文”回答事实。
6. 不破坏 Widget 按钮已正常的 action path。
7. 不破坏单工作流调试中已经正确的 context merge。
8. 首轮请求无历史上下文时行为必须与现在一致。

### 8.3 需要新对话优先调查的 ADP 能力

请先确认腾讯云智能当前应用层是否提供以下任一种能力，然后选择最稳妥实现，而不是凭印象：

- 应用级多轮上下文是否默认传给“思考模型”
- 工作流选择时是否能读取对话历史 / 上一轮工作流输出
- 是否支持 Agent 节点、工作流节点、变量聚合/赋值、会话变量、全局变量等持久化
- Widget action 与用户文本消息进入顶层路由时的 payload 差异
- 应用角色指令是否只能文本提示、不能做结构化 session state

若平台本身不能给顶层路由稳定历史，则考虑一个**统一的“00-应用上下文路由/Follow-up Resolver”** 或一个最小化上下文解析层，但必须先证明 ADP 支持它在路由前/路由中介入。

### 8.4 不要做的事

- 不要把 5 个稳定工作流合成一个巨型工作流，除非有明确平台证据且收益远大于风险。
- 不要因为 app follow-up 失败就改坏工具 API 参数。
- 不要把 Widget 按钮 action 改成纯 prompt hack。
- 不要回退 v2。
- 不要让模型自行补造上轮课程/教室数据。
- 不要只追加更多角色指令文本然后宣称修好了；必须有应用层实测闭环。

## 9. R47 复验矩阵（新对话必须记住）
