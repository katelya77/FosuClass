## 2. 产品定位与硬边界

应用名：**校园智序·小序**

定位：面向高校课程、教学空间与校园教学运行任务的智能助手 / 校园教学时空决策智能体。

核心原则：

1. 自然语言负责理解任务；**动态校园事实必须来自确定性工作流 / CampusTools 核验**。
2. 工具失败、参数不足、演示数据范围外时，不允许模型补造课程、教室、教师、冲突、教学态势等动态事实。
3. 静态功能说明、怎么问、功能示例、产品边界可直接回答，不必调工具。
4. 当前为比赛匿名数据：用户侧只使用 A/B/C 校区、T01～T12、G01～G06 等匿名标识，不恢复真实学校/老师/班级身份。
5. 当前以查询/规划/分析为主，不能伪装成真实教务写入、选课、改课、预约教室。
6. Widget 是演示体验的重要组成，但视觉层不能修改工具事实。
7. 评委体验优先：界面要直观、简洁、能快速知道“下一步能做什么”，但任何 UI 优化不得破坏执行链。

2. 其他 slot 继承上一轮 confirmed state。
3. 本轮若明确切换任务，允许跨工作流，但携带兼容 slots。
4. 真实歧义才追问；不要把“本轮没重复实体”当成缺参。
5. 首轮无历史时，`只看周三` 应合理追问，不得伪造历史。
6. 所有动态事实最终仍由 01～05 / CampusTools 输出。
7. Widget button path 保持原样，不要改坏。
8. 01/02/04 工作流内部已有 context merge，除非有直接回归证据，不要重写。

### 新对话必须优先调查的腾讯 ADP 平台能力

先基于腾讯官方文档/当前真实控制台能力确认：

- 思考模型是否获得多轮对话历史
- 工作流选择是否能读取上一轮工作流输出
- 是否有会话变量 / 全局变量 / session state / conversation variables
- Agent 节点、工作流节点、变量聚合/变量赋值能否在多轮持久化
- Widget action payload 与自由文本消息进入顶层路由的差异
- 是否支持在 5 工作流之前加入统一 Follow-up Resolver
- 如果顶层不支持状态持久化，能否用一个最小 `00-应用上下文路由` / CloudBase session-state service 安全实现

### 推荐设计原则

优先级从高到低：

1. **平台原生会话变量 / structured state**（最优，如果有）
2. **统一 Follow-up Resolver / 00 context-router**（如果能在工作流选择前介入）
3. **CloudBase 轻量 session state**，以 conversation/session key 存 last confirmed slots（平台原生能力不足时）
4. 最后才是 prompt 补强；prompt 只能辅助，不可作为唯一状态层

不要把 5 个稳定工作流粗暴合成一个巨型工作流，除非平台证据证明这是唯一稳定路径。
